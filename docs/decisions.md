# 設計判断の記録(ADR)

新しい判断は末尾に追記する。既存の判断を覆す場合は、元のエントリに「→ ADR-XXX で変更」と注記し、新エントリを書く。

---

## ADR-001: バックエンドなしの完全ローカル構成

- **日付**: 2026-07-03
- **決定**: サーバー・DB・認証を持たず、全データを端末の IndexedDB に保存する静的 PWA とする
- **理由**: 費用ゼロ要件、オフライン動作、入力応答速度(ネットワーク往復ゼロ)の 3 要件を同時に満たす。個人利用でマルチデバイス同期は必須でない
- **トレードオフ**: 端末紛失・ブラウザデータ削除でデータ消失のリスク → JSON エクスポート/インポートと `storage.persist()` で緩和。クラウド同期はバックログ

## ADR-002: React + Vite + TypeScript

- **日付**: 2026-07-03
- **決定**: UI は React、ビルドは Vite、TypeScript strict
- **理由**: エコシステムが最も厚く、Dexie(dexie-react-hooks)・Chart.js・PWA プラグインの組み合わせ実績が豊富。長期継続開発での情報量を優先
- **却下案**: Svelte/SolidJS(バンドルは小さいが周辺ライブラリと知見の蓄積で劣る)、vanilla TS(開発速度と保守性で不利)

## ADR-003: Dexie.js(IndexedDB)+ useLiveQuery

- **日付**: 2026-07-03
- **決定**: データ層は Dexie.js。UI への反映は dexie-react-hooks の `useLiveQuery` に任せ、別途の状態管理ライブラリは入れない
- **理由**: 書き込み→自動再クエリで「保存ボタンなし・即時反映」の入力 UX が最小コードで実現できる。バージョン付きマイグレーション機構が長期運用に向く
- **却下案**: localStorage(容量・構造化クエリ不可)、Zustand/Redux 併用(データの二重管理になる)

## ADR-004: ホスティングは GitHub Pages + hash ルーティング

- **日付**: 2026-07-03
- **決定**: GitHub Actions で GitHub Pages にデプロイ。SPA ルーティングは hash 方式
- **理由**: リポジトリと配信が同居し無料。Pages は 404 フォールバックがないため history ルーティングはリロードで壊れる → hash が安全
- **却下案**: Cloudflare Pages / Netlify(無料で優秀だが、アカウントを増やさず GitHub に集約する方を優先。移行は容易なので問題が出たら再検討)

## ADR-005: タグは全種目共通のマスタ、「タグなし」は空文字で正規化

- **日付**: 2026-07-03
- **決定**: タグ(高重量日など)は種目に紐づかない共通マスタとし、`sets.tagId` の複合インデックス `[exerciseId+tagId]` を分析の基本単位とする。タグ未指定は `tagId: ''` に正規化
- **理由**: 同じタグ体系を複数種目で使い回せる。IndexedDB の複合インデックスは `undefined` を含むレコードを引けないため、空文字への正規化が必要
- **却下案**: 種目ごとの子種目(variant)を別レコードで持つ(種目マスタが膨れ、タグ横断のフィルタが難しくなる)

## ADR-006: MAX 記録はキャッシュせず都度計算

- **日付**: 2026-07-03
- **決定**: MAX(最大重量・回数・推定 1RM)は専用テーブルを持たず、`[exerciseId+tagId]` インデックスから都度計算する
- **理由**: 想定データ量(10 年で数万セット)ならインデックススキャンで十分速い。キャッシュを持つと編集・削除・日付間コピー/移動のたびに整合性維持が必要になり、バグの温床になる
- **再検討条件**: 実測でグラフ/MAX 表示に体感遅延が出たら、集計キャッシュか Web Worker 化を導入

## ADR-007: 推定 1RM は O'Conner 式

- **日付**: 2026-07-03 → 2026-07-07 変更
- **決定**: `1RM = weight × (1 + reps / 40)`。計算は `lib/` の純粋関数に隔離
- **理由**: 当初は Epley 式(`/30`)を採用していたが、ユーザーの要望により O'Conner 式(`/40`)へ変更。O'Conner 式は Epley より保守的(低め)な推定値を出し、実際の挙上感覚に近いとされる。関数が純粋関数に隔離されているため差し替えは 1 行の変更で済む

## ADR-008: Pages へのデプロイは gh-pages ブランチ方式(legacy)

- **日付**: 2026-07-03
- **決定**: GitHub Actions からのデプロイは `actions/deploy-pages`(artifact 方式)ではなく、ビルド成果物を `gh-pages` ブランチへ force push する legacy 方式にする(ADR-004 の補足)
- **理由**: artifact 方式が M2 デプロイ時から "Deployment failed, try again later" で連続失敗(ビルドは成功、GitHub ステータス正常、API にエラー詳細なし、新 SHA・新 artifact でも再現)。gh-pages ブランチ方式は枯れており動作が追いやすい
- **備考**: Pages 設定は `build_type=legacy` / source=gh-pages ブランチに API で変更済み。`.nojekyll` を dist に含めて Jekyll 処理を回避

## ADR-009: ロック中の鳴動は iOS ショートカット連携を任意オプションで追加

- **日付**: 2026-07-08
- **決定**: 既存の Web Audio + Wake Lock タイマーは残したまま、設定 `nativeTimerEnabled`(既定 OFF)で iOS「ショートカット」経由の標準タイマー起動を追加する。ON 時はタイマー開始で `shortcuts://run-shortcut?name=<名前>&input=<秒>` を開き、PWA 側の音/Wake Lock/カウントダウンは動かさず完全にネイティブへ委譲する
- **理由**: iOS PWA は画面ロック(電源ボタン)で Wake Lock 解除 + AudioContext suspend となり終了音が鳴らない。標準の時計アプリのタイマーはシステム管理でロック中も確実に鳴る。`shortcuts://` は Apple 公式サポートで、standalone PWA から確認ダイアログなしで起動・ロック中鳴動・(ショートカット末尾の「URLを開く」で)PWA 自動復帰まで実機確認済み
- **却下案**: (1)Web Audio を完全に置き換える → ショートカット未作成ユーザーが使えなくなる/開始のたび時計アプリへ画面遷移するデメリットを全員に強制するため却下、オプトインとした。(2)標準の Clock URL スキーム直叩き → 時計アプリを開くだけで秒数を渡せない(公式に duration パラメータ非対応)ためショートカット経由が必須
- **制約**: ショートカットはユーザーが手動作成(アプリから配布不可)。名前は `nativeTimerShortcutName` と一致必須。同時に走る標準タイマーは 1 つ(既存を上書き)

## ADR-010: 追加専用インポート(プラン取り込み)を新設

- **日付**: 2026-07-09
- **決定**: 既存の「復元」(`importData`、全テーブル clear→置換)とは別に、既存データを一切壊さず
  追加のみ行うインポート経路を新設する。専用の小さな JSON フォーマット(`kind: 'plan-import'`、
  種目名・タグ名で指定、内部 id 不要)を受け取り、`date + exerciseId + tagId` の組み合わせで
  既存 `sets` が 1 件でもあればその項目を丸ごとスキップする(冪等)。種目・タグは name 一致で
  照合し、なければ新規作成する。スキーマ変更はしない(`reps: 0` を「未実施(予定)」として
  週間集計・MAX 判定から除外する既存ルールをそのまま「予定」の表現に流用する)
- **理由**: 別プロジェクトで管理する週次トレーニングプランを毎週取り込みたいが、全置換の復元機能
  では毎回「過去記録込みの全エクスポート」を往復させる必要があり容量・手間が過大(`docs/plan-import-guide.md`
  で検討済み)。追加専用・小フォーマットにすることで、外部プロジェクト側は当日以降の予定行だけを
  含む小さな JSON を生成すればよくなる
- **却下案**: (1)既存 `importData` をマージモードに拡張する → 全置換という単純さ・安全性
  (誤ったバックアップでの汚染防止)を失うため、別関数として独立させた。(2)専用の `isPlanned`
  フラグを `sets` に追加する(Dexie マイグレーション要) → `reps: 0` の除外ルードが既に同じ
  目的を果たしており、スキーマ変更のコストに見合わないため見送り。将来トレース性が必要になれば
  再検討
- **制約**: 上書き・マージ更新はサポートしない(スキップのみ)。既に記録がある日×種目×タグへ
  プラン側の変更(重量変更など)を反映したい場合は、ユーザーが手動で編集する必要がある
  → **ADR-012 で変更**(上書きをオプションとして追加)
- **追記(2026-07-10)**: 実機テストで、デフォルト 7 部位にない `bodyPart`(例: "体幹")を指定した
  新規種目が `bodyParts` マスタに登録されず、種目選択・種目管理のタブ UI から選べなくなる不具合を
  発見。新規種目作成時に `bodyPart` も name 一致で `bodyParts` マスタへ同様に自動作成するよう修正
  (`computePlanActions` に `createBodyParts` を追加)

## ADR-011: 感想メモ(日全体・種目ごと)の保存設計

- **日付**: 2026-07-10
- **決定**: セット単位の 1 行メモ(`sets.memo`)に加え、2 つの粒度の感想メモを追加する。(1)**日全体**は
  既存の `days.note`(型に予約済み・未使用)をそのまま使う。(2)**種目ごと(ブロック=種目×タグ単位)**は
  専用テーブル `blockNotes`(複合主キー `[date+exerciseId+tagId]`、`db.version(7)`)を別立てにする。
  タグ変更・種目変更・別日コピー/移動ではブロックのキーが変わるため、repository の該当関数
  (`changeBlockTag`/`changeBlockExercise`/`transferSets`)でメモのキーも追従させ、キー衝突時は
  改行連結で合流(`mergeNotes`)。ブロックが空になった時(`deleteSet` で最後のセット削除)は
  孤児メモを削除する
- **理由**: ブロックは永続レコードを持たない(`sets` の集合でしかない)ため感想の保存先が無い。
  `days` が場所メタを別テーブルで持つのと同じ発想で専用テーブルに分離する方が、全セットへ
  冗長コピーする方式よりも一貫性を保ちやすく、空ブロック(セット 0 件)にも書ける
- **スコープ外**: 日全体メモ(`days.note`)は日付に紐づくものとし、`transferSets` では移動先へ
  引き継がない(現状 `locationId` も引き継がない挙動と一致)。ブロックメモは追従させる
- **却下案**: (1)`WorkoutSet` に `blockNote?` フィールドを持たせ全セットへ複製 → 編集時に N 件同期・
  空ブロックに書けない・統合時の衝突処理が煩雑なため却下。(2)日全体メモも専用テーブル →
  `days.note` が既にあり不要
- **バックアップ**: `blockNotes` は `setAttributes`/`templates` と同じ省略可オプショナル配列として
  export/import に追加。`days.note` は Day レコードごと入出力済みで自動対応。`BACKUP_FORMAT_VERSION`
  は据え置き(1、非破壊の追加のみ)

## ADR-012: プラン取り込みに上書きオプションを追加

- **日付**: 2026-08-19
- **決定**: ADR-010 で「スキップのみ」としていたプラン取り込みに、既存記録がある日×種目×タグ
  (ブロック)を丸ごと削除して新しいセットに置き換える「上書き」をオプションとして追加する。
  既定は従来どおりスキップ(非破壊)。`PlanImportModal` に「重複分を上書きする」トグルを設け、
  ON にすると取り込み実行時に重複ブロックの一覧を `window.confirm` で提示し、承認後に適用する。
  `computePlanActions(file, existing, { overwrite })` が overwrite の有無で重複ブロックの行き先を
  `skipBlocks`(既定)/`overwriteBlocks`(overwrite 時)に振り分け、`applyPlanImport` は
  `overwriteBlocks` に該当する既存セットを削除してから新セットを追加する。上書き対象ブロックの
  `orderInDay` はその日の末尾に振り直す(タグ変更・種目変更の統合時と同じ挙動)
- **理由**: 週次プランを毎回取り込む運用で、既に登録済みの予定行(例: 重量変更)を反映したい
  ニーズが発生。ユーザー要望により「置き換え可」の仕様に変更。誤操作防止のため、上書きは
  明示的なトグル + 確認ダイアログを介した時のみ発生する(既定の取り込みは従来どおり安全)
- **スコープ外**: `blockNotes`(種目ごとメモ)はブロックの識別キー(date+exerciseId+tagId)が
  上書きでも変わらないため、削除・引き継ぎ処理は不要(触らない)
- **却下案**: ブロック単位の個別チェックボックスで上書き/スキップを選択させる案 → 週次プランの
  用途では「今回の重複は全部反映する/しない」の一括判断で十分であり、UI・実装が複雑になる
  個別選択は見送り(必要になれば再検討)

## ADR-013: プラン欄とユーザー欄を別フィールドに分離する

- **日付**: 2026-08-20
- **決定**: プラン取り込みが書く内容と、ユーザーがジムで書く内容を、同じメモ欄に混ぜず別フィールドに
  分ける。セット単位は `sets.planMemo`(プラン)と `sets.memo`(ユーザー)、種目×タグ単位は
  `blockNotes.planNote`(プラン)と `blockNotes.note`(ユーザー)。プラン取り込みは planMemo /
  planNote だけを書き、ユーザー欄には一切書き込まない。UI ではプラン欄を「予定」ラベル付きの
  読み取り専用表示(記録画面のみ)とし、入力欄はユーザー欄のまま
  - 上書き取り込み(ADR-012)は既存セットを削除して作り直すため、削除前に既存セットの `memo` を
    セット順(orderInDay 昇順)で保持し、新しいセットの同じ位置へ引き継ぐ。`blockNotes` は行を
    put で更新し、`note`(ユーザー欄)を保ったまま `planNote` だけ差し替える
  - プランファイル側は既存キー `sets[].memo` をそのまま「そのセットの指示」として受け取り
    (取り込み時に planMemo へ入る)、種目単位の指示用に `items[].note` を追加した
  - インデックスを増やさない追加フィールドのため Dexie の version 上げ・マイグレーションは不要
    (既存レコードは planMemo / planNote が undefined のまま。ADR-012 以前に取り込んだプランの
    文言は `memo` に残るが、実施済みの過去データなので移送はしない)
- **理由**: プランの指示をセットメモに書く運用で、(1) 指示が長文化して記録画面の視認性が落ちる、
  (2) ユーザーが実施中にメモへ追記すると上書き取り込みで消える、(3) プラン生成側から見て
  「自分が書いた指示」と「ユーザーの実績メモ」が判別できない、という 3 つの問題が同時に起きていた。
  欄を分ければ、ユーザーはどこに何を書いても取り込みで壊れず、生成側もユーザーの書き込みを
  読み取り専用の情報として扱える
- **併せて決めた運用**: プラン文の書式ルール(何をどれだけ・フォーム注意点・中止条件だけを書き、
  重量選定の経緯や理論的背景は書かない。種目共通の内容は `items[].note` に 1 回だけ)を
  `docs/plan-import-guide.md` に明文化した
- **却下案**: (a) 接頭辞マーカー(`[P] …`)で 1 つの欄を区切る → 取り込み時のテキスト分割が
  ユーザーの書き方に依存して壊れやすい。(b) 上書き取り込みをやめて未実施日限定にする運用ルール
  だけで済ませる → ユーザー欄の保護はできるが、長文化と生成側の判別不能は解決しない

## ADR-014: 体調・やる気スコアと痛み記録(部位は文字コードで保存)

- **日付**: 2026-09-23
- **決定**: 日ごとの「体調」「やる気」を 1〜10 の数値、「痛み」を構造化レコードで記録する専用画面
  (`/condition?date=`)を新設し、記録画面の場所チップ横の要約ボタンから開く。テーブルを 2 つ追加する
  (`db.version(8)`)
  - `conditions`(主キー `date`): `{ date, condition?, motivation? }`
  - `painRecords`(`id, date, area, [area+side]`): 1 日 1 部位×左右ごとに 1 レコード。部位は画像では
    なく **文字コード**(`area` 例 `knee`、細かい場所 `regionIds[]` 例 `knee.medial`。同じ関節の
    複数箇所が痛むことがあるため配列)で保存し、人体図 SVG は
    UI の入力手段としてのみ使う。強さは医療現場標準の NRS(0〜10)、種類・痛む時・痛む動き・
    発症の仕方は固定コードの選択式(複数可)、関連種目は `exerciseId[]`、補足は自由記述 `note`
  - 部位の分割は整形外科の診察で使う単位(例: 肘=外側上顆/内側上顆/肘頭/前面、膝=膝蓋骨周囲/
    膝蓋腱/内側/外側/膝窩)に合わせ、`src/lib/painRegions.ts` に定義する。左右は患者本人から見た
    左右(人体図の正面図では画面の左が「右」)。体幹は中央/右/左/両側
  - 痛みの経過は「部位(area)×左右」単位でまとめ、経過画面(`/condition/pain`)で初回・最新・
    強さの推移・記録一覧を表示し、受診時に見せる要約テキストをコピーできる
  - 入力負荷を下げるため、直近 14 日以内に記録があり最後の強さが 1 以上の痛みを「続いている痛み」
    として提示し、1 タップで前回内容を引き継いで今日の記録を作れる(0=今日は痛くない、も 1 タップ)
- **理由**: (1) `days` に混ぜると「日レコードが既にある=場所の既定値を付けない」判定(ホームジム #3)
  や `transferSets` の日削除に巻き込まれるため別テーブルにする。(2) 画像保存は容量が大きく、
  集計・経過比較もできない。コード化すれば数十バイト/件で、医師に渡す文章も自動生成できる。
  (3) 1〜10 はユーザー指定(回答 2026-09-23)
- **既存の日メモ**: `days.note`(自由記述)は残す。過去に書いた体調メモの自動変換はしない
- **バックアップ**: `conditions` / `painRecords` を省略可オプショナル配列として export/import に追加。
  `BACKUP_FORMAT_VERSION` は据え置き(1、非破壊の追加のみ)
- **却下案**: (a) 下部タブに「体調」を追加 → タブが 6 個になり狭い(ユーザー判断で記録画面から開く)。
  (b) 体の部位を自由記述 → 表記ゆれで経過をまとめられず、医学的な部位の区別も付かない
- **追記(2026-09-23, v1.0.28)**: ユーザー要望で部位に「頭」(`head`)を追加。区分は頭痛の診察で
  種類の見当をつける場所(おでこ/こめかみ/頭頂部/後頭部/目の奥/頭全体)+顎関節(重い挙上時の
  食いしばり)。緊張型頭痛の特徴に合わせ痛みの種類に `pressing`(締め付けられる・圧迫感)を追加。
  頭で「始まり方=急に」または強さ 8 以上のときは、入力画面に受診を促す注意を表示する
  (運動中の突然の激しい頭痛は くも膜下出血 等の可能性があるため。`isHeadacheWarning`)

## ADR-015: 同じ種目を「回目(round)」で分け、実施順どおりに記録する

- **日付**: 2026-10-10
- **決定**: 1 日の中の種目ブロックの単位を「種目×タグ」から「種目×タグ×回目(`round`)」に広げる。
  ベンチプレス 2 セット → ダンベルカール 3 セット → ベンチプレス 3 セット を、3 つの別ブロックとして
  実施順に記録・表示できるようにする
  - `sets.round?: number`(省略 = 0 = その日の 1 つ目)。**番号はブロックの識別子**で、表示の
    「1回目・2回目」は画面上の並び順から振る(並べ替えれば表示も入れ替わる)。同じ種目×タグが
    1 日に 1 ブロックしかなければ回目の表示はしない
  - 種目メモ・プラン指示(ブロックメモ)も回目ごとに別々に持つ。Dexie は主キーを変更できないため、
    新テーブル `blockNotesV2`(主キー `[date+exerciseId+tagId+round]`)を `db.version(9)` で作って
    旧 `blockNotes` の行を `round: 0` で移し、`db.version(10)` で旧テーブルを削除する
  - 記録画面: 「＋ 種目を追加」で、その日に既にある種目×タグを選ぶと、一番下に新しい回目の
    ブロックができる(従来は既存ブロックに合流していた)
  - タグ変更・種目変更・別の日へコピー/移動で、行き先に同じ種目×タグが既にある場合も**合流させず**
    別の回目として残す(実施順を保つ。従来は末尾に連結・メモを合流していた)
  - 前回コピー: 前回の日に同じ回目があればそれを、無ければ前回の日の最初のブロックをコピーする
  - プラン取り込み: `items` の並び順をそのまま実施順とし、同じ日に同じ種目×タグを複数書けば
    2 つ目以降は別の回目として取り込む(フォーマットへの項目追加はなし。生成側は同じ種目を
    複数回書くだけ)。スキップ/上書きの照合は「日付×種目×タグ×回目」で行い、上書きしたブロックは
    元の位置に置き換える
  - 履歴・グラフ・MAX 記録・週間集計は従来どおり「種目×タグ×日」単位(回目は区別しない)
- **理由**: ユーザー要望(2026-10-10、回答: 種目を追加で同じ種目を選ぶ/メモは回目ごと/取り込みは
  並び順そのまま)。連続したセットの「かたまり」から自動でブロックを作る案もあるが、並べ替えで
  2 つが隣り合うと勝手に合流してしまうため、明示的な番号を持たせる
- **バックアップ**: 書き出しの `blockNotes` 配列の各要素に `round` を追加(読み込み時、無ければ 0)。
  `sets[].round` も追加(省略可)。`BACKUP_FORMAT_VERSION` は据え置き(1、旧ファイルもそのまま読める)
- **却下案**: (a) orderInDay の連続区間をブロックとみなす(スキーマ変更不要だが、上記の勝手な合流と、
  ブロックメモの持ち主が決められない問題がある)。(b) ブロックメモは日×種目×タグで 1 つのまま
  (ユーザー判断で回目ごとに分ける)

## ADR-016: プラン取り込みの上書き方法を 3 択にし、「同日を全て置き換え」を追加

- **日付**: 2026-10-10
- **決定**: ADR-012 の「重複分を上書きする」トグルを、次の 3 択(`PlanImportMode`)に置き換える
  1. `skip`(上書きしない・既定): 従来どおり。重複ブロックはスキップ
  2. `overwrite`(重複のみ上書き): 従来の上書き。重複ブロックだけ元の位置で置き換え、他は残す
  3. `replaceDay`(同日を全て置き換え): ファイルに含まれる**日付ごとに、その日の全セットを削除してから**
     ファイルの items を並び順どおりに入れ直す。新プランに無い種目はその日から消える
  - `replaceDay` で消すのはその日の**全セット**(手入力の実績も含む)。プラン由来のセットを見分ける
    印がない(`planMemo` はプランにセットメモがあるときしか入らない)ため。代わりにプレビューと確認
    ダイアログで「削除される種目」(`removeBlocks`)を一覧表示する
  - 新プランにも同じ日付×種目×タグ×回目がある場合は「上書き」扱いとし、ユーザーが書いたセットメモ
    (セット順)・種目メモは引き継ぐ(ADR-013)。新プランに無いブロックの種目メモ・プラン指示は削除する
  - 日メモ・体調・痛み記録は消さない。場所はファイルに `location` があればその日に適用する
    (`skip`/`overwrite` は従来どおり新規の日のみ)
  - 並びはファイルの items 順(上書き分も元の位置ではなく新プランの位置)
- **理由**: ユーザー要望(2026-10-10)。週次プランを作り直して取り込むと、`overwrite` では新プランで
  採用しなかった種目が残り、新旧どちらのプランの種目か画面上で判別できなかった
- **却下案**: プラン由来のセットだけを消す(セットに由来フラグを持たせる)→ 既存データには印がなく
  過去の取り込み分を判別できないうえ、取り込んだ予定に実績を書き込んだセットの扱いが曖昧になる。
  ユーザーの定義(「一度消してから、新しく入れ込む」)どおり日単位で消し、確認画面で明示する

## ADR-017: 体重の日ごとの記録(`bodyWeights` テーブル)と、自重換算への反映

- **日付**: 2026-10-11
- **決定**: 体重を 1 日 1 件(kg、小数第二位まで)で記録する専用テーブル `bodyWeights`
  (主キー `date`、Dexie v11)を追加する
  - 入力は体調画面(`/condition`)。体調・やる気と同じく日付に紐づく自己記録のため
  - 推移グラフは分析タブに「体重」を追加して表示する(Chart.js、既存のグラフと同じ遅延読み込み)
  - 自重セットの「体重 + 加重」換算(1RM・総負荷量・MAX 判定)は、**そのセットの日の体重**
    (無ければその日より前の直近の記録)を使う。それより前に記録が無い場合は、従来の設定
    「体重」(`settings.bodyWeight`)を使う
  - バックアップの書き出し/読み込みに `bodyWeights` を追加(省略可配列。`BACKUP_FORMAT_VERSION` は据え置き)
- **理由**: ユーザー要望(2026-10-11、回答: 手入力のみ/体調画面で入力・分析でグラフ/その日の体重で
  計算/1 日 1 件)。体重が変わっても過去の自重セットの換算値が変わらないようにする
- **却下案**: (a) iPhone のヘルスケア連動 → PWA からは HealthKit に直接アクセスできない。
  ショートカット経由の取り込みは可能だが、ユーザー判断で手入力のみとした(必要になれば ADR-009 と同じ
  URL スキーム方式で追加できる)。(b) `conditions` テーブルに体重列を足す → 体調・やる気が両方
  未設定になると行を消す既存ロジックと絡むため別テーブルにした。(c) 最新の体重で設定値を更新する
  → 過去分も最新体重で再計算されてしまう

## ADR-018: セットの左右を「無 → 右 → 左」の切り替えボタンにする

- **日付**: 2026-10-19
- **決定**: セット行の「W」「自」の隣に、タップごとに 無 → 右 → 左 → 無 と切り替わる固定ボタンを置く
  - データは従来どおりセット属性 `attributes` の `'右'` / `'左'`(無のときはどちらも付けない)。
    スキーマ変更なし。過去データ・プラン取り込み(`attributes: ['左']`)・属性での集計はそのまま使える
  - 左右は排他なので、切り替え時はもう一方を必ず外す。両方付いた古いデータは `'右'` として表示し、
    次のタップで正規化する
  - 左右はクイック属性ボタン・属性選択モーダルの候補から外し、属性選択で新規作成もさせない。
    既定のクイック属性は `['フル']` に変更。旧設定に `'右'` `'左'` が残っていても未設定として扱う
- **理由**: ユーザー要望(2026-10-19)。左右は排他なのに、自由な属性として両方付けられた
- **却下案**: セットに専用列 `side` を追加 → 既存データの移行・バックアップ形式・プラン取り込みの変更が
  必要になる割に、属性のままで要件を満たせる
- **見送り**: 同時に要望のあった「Siri で体重を記録」はユーザー判断で見送り(サーバーが無いため、
  アプリを開かずに記録する方式は取れない。必要になれば ADR-017 の URL スキーム方式で検討する)

## ADR-019: プラン取り込みの上書きで、実績のあるセットを既定で守る

- **日付**: 2026-10-19
- **決定**: 「重複のみ上書き」「同日を全て置き換え」(ADR-016)で消える対象に**実績のあるセット**が
  含まれる場合、プレビューと確認ダイアログで予定だけのセットと区別して警告し、既定では残す
  - **実績の判定は `reps > 0`**。プラン取り込みは `reps` 省略時 0(=未実施の予定)で入り、
    ジムで回数を書き込むと実績になる。週間集計・MAX 判定が「reps 0 = 予定」として除外している
    のと同じ基準。プランが `reps` を指定したセットも実績とみなされる(誤って消すより誤って残す側に倒す)
  - 判定はブロック(日付×種目×タグ×回目)単位。1 セットでも実績があればそのブロックは「実績あり」
  - 取り込み画面に「実績のある種目は残す」チェック(既定オン)を置く(`keepPerformed`)。オンのとき、
    実績ありブロックは削除も上書きもせずそのまま残し、プランの同じブロックは取り込まない。
    `replaceDay` で残したブロックはその日の先頭側に残り、プランの種目はその後ろに入る
  - オフにした場合は従来どおり消えるが、確認ダイアログの先頭に「実績が入ったセットが N セット消えます」と
    強く警告する。プレビューでも実績ありブロックに「実績 N セット」を表示する
  - プランファイルに任意の最上位キー `recommendedMode`(`'skip' | 'overwrite' | 'replaceDay'`)を追加。
    あれば取り込み画面の上書き方法の初期値にする(ユーザーは変更できる。不明な値は無視)。
    `keepPerformed` の既定オンは `recommendedMode` に関係なく変わらない
  - スキーマ変更なし。`PLAN_IMPORT_FORMAT_VERSION` は据え置き(1、旧ファイルもそのまま読める)
- **理由**: 依頼(2026-10-19、project_ERGO 経由・ユーザー承認済み)。週の途中で予定を作り直して
  「同日を全て置き換え」を選ぶと、手で入れた実績も消えていた(プレビューで赤表示されるだけ)
- **却下案**: (a) セットにプラン由来/編集済みの印を持たせて判定 → 既存データに印が無く、過去の取り込み分を
  判別できない(ADR-016 と同じ理由)。(b) 実績があれば取り込み自体を中止 → 予定部分だけ更新したい
  通常の使い方ができなくなる
